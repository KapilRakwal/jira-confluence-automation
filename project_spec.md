# Technical Specification: Team Workload & Delivery Dashboard

**Version:** 1.0 · **Date:** 2026-11-23 · **Owner:** Kapil Rakwal (Delivery Manager)

---

## 1. Overview

A daily-refreshed, static HTML dashboard giving the delivery manager visibility into
workload balance and delivery flow for a ~10-person team working on a POC that must
complete by **end of November 2026**. The dashboard is generated by a Python script
from Jira Cloud data and shared with stakeholders as a file/link.

## 2. Goals

- See at a glance who is overloaded or idle (workload balance).
- Track how fast work moves (cycle time, lead time) over the last 2 weeks.
- Surface at-risk work visually, given the hard end-of-November deadline.
- Zero manual data gathering; refreshes automatically every morning.

### Non-goals (out of scope)

- Live/interactive web app, user login, or write-back to Jira.
- Historical data warehouse; each run reads Jira directly.
- Sprint ceremonies reporting (covered by the separate weekly status report tool).

## 3. Users & Audience

| Role | Use |
|---|---|
| Delivery manager (primary) | Reviews daily, rebalances work, escalates risks |
| Stakeholders | View shared HTML file/link; read-only |

## 4. Data Sources

| Source | Scope | Access |
|---|---|---|
| Jira Cloud | Project **SCRUM** on `kapilrakwal.atlassian.net` | REST API v3 + Agile API, Basic auth (email + API token) |

- **Team identification:** all distinct assignees found on issues in the SCRUM
  project within the reporting window. No hard-coded roster.
- **Reporting window:** rolling **last 14 days** (configurable).

## 5. Metrics & Definitions

| Metric | Definition | Source fields |
|---|---|---|
| **Open issues per person** | Count of issues with `statusCategory != Done`, grouped by assignee (incl. "Unassigned") | assignee, status |
| **Cycle time** | Days from first transition into an *In Progress* status category → transition into *Done*, per issue; report median and per-person average for issues completed in window | changelog (status transitions) |
| **Lead time** | Days from issue `created` → `resolutiondate`, for issues completed in window; report median | created, resolutiondate |

### Risk highlighting rules (dashboard-only, no notifications)

An issue/row is highlighted when any of:
- Not Done and **no update in ≥ 3 days** (stale — tight threshold due to deadline).
- Priority is Highest/High and not Done.
- Due date (if set) is past, or after **2026-11-30** (POC deadline breach).

## 6. Dashboard Content & Layout

Single self-contained HTML file (inline CSS + JS, no external build):

1. **Header:** project, generation timestamp, days remaining until 2026-11-30.
2. **Summary cards:** total open, completed in window, median cycle time, median lead time, # at-risk items.
3. **Workload chart:** horizontal bar chart — open issues per assignee (highlight > team average).
4. **Throughput/flow chart:** line or bar — issues completed per day over the window.
5. **Cycle/lead time table:** per-person averages + team median.
6. **At-risk items table:** highlighted rows with reason (stale / high priority / overdue).
7. **Full open-work table:** key, summary, assignee, status, days in status, due date.

**Charts:** rendered with **Chart.js loaded from CDN** with a graceful fallback note
if offline (tables always work offline).

## 7. Architecture

```
dashboard/
├── dashboard.py          # single-file generator
├── .env                  # credentials (gitignored)
├── .env.example
├── .gitignore
├── schedule_task.ps1     # Windows Task Scheduler registration (daily 08:00)
└── output/
    └── dashboard.html    # overwritten each run (stable path for sharing)
```

### Flow

1. Load config from `.env`.
2. Fetch issues updated/completed in window via `/rest/api/3/search/jql`
   (fallback to legacy `/rest/api/3/search`), including `changelog` for transitions.
3. Compute metrics in pure Python (no pandas; stdlib + `requests` only).
4. Render HTML from an inline template; write atomically to `output/dashboard.html`.
5. Exit non-zero with a clear message on auth/network failure (visible in Task
   Scheduler history).

### Configuration (`.env`)

| Key | Example | Notes |
|---|---|---|
| `ATLASSIAN_SITE` | `https://kapilrakwal.atlassian.net` | |
| `ATLASSIAN_EMAIL` | account email | |
| `ATLASSIAN_TOKEN` | API token | **unscoped** token; never committed |
| `JIRA_PROJECT` | `SCRUM` | |
| `WINDOW_DAYS` | `14` | reporting window |
| `STALE_DAYS` | `3` | stale threshold |
| `POC_DEADLINE` | `2026-11-30` | drives countdown + overdue rule |

## 8. Scheduling & Operations

- **Windows Task Scheduler**, daily at **08:00**, via `schedule_task.ps1`.
- Output path is stable (`output/dashboard.html`) so a shared link/shortcut always
  shows the latest data; stakeholders just refresh the page.
- Manual run supported: `python dashboard.py`.

## 9. Security

- Credentials only in `.env`, which is gitignored; `.env.example` ships placeholders.
- Read-only API usage; no data sent to third parties (Chart.js CDN serves JS only).
- Dashboard HTML contains work-item data — share only with authorized stakeholders.

## 10. Acceptance Criteria

1. Running `python dashboard.py` with valid `.env` produces `output/dashboard.html`
   with all sections in §6 populated from live SCRUM data.
2. Workload chart shows every assignee with ≥1 open issue, plus "Unassigned".
3. Cycle time uses actual status-transition timestamps from the changelog, not
   created date.
4. An issue untouched for 3+ days appears highlighted in the at-risk table with
   reason "stale".
5. Scheduled task runs daily and overwrites the output file; failures are visible
   in Task Scheduler history.
6. Script fails fast with a readable error when the token is invalid.
